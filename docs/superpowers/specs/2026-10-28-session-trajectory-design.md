## 1. 问题与设计原则

### 1.1 现状的问题

- **代理运行页**同时放了状态卡、4 项事实、监控图表、连接表、入口卡片、日志、监听设置弹窗。"监控""连接""条目"三个 tab 的数据都来自同一份 `monitor` 快照，只是切法不同。
- **模型用量页**有两层筛选（日期 + 模型下拉）和三个 tab，"记录"tab 只能看到一行行 token 数，看不出这次请求是在做什么。
- **完全没有"代理到底替我的 Agent 做了什么"这一视角**。`session_id` 请求头已经被转发（`core/src/proxy/headers.rs`），但从未落库。

### 1.2 设计原则

1. **一页只回答一个问题，只对应一个时间尺度。**


   | 页面 | 回答的问题                           | 时间尺度               |
   | ------ | -------------------------------------- | ------------------------ |
   | 运行 | 代理现在是否正常，此刻有哪些请求在跑 | 实时（内存，不持久化） |
   | 会话 | 我的 Agent 在某次会话里做了什么      | 逐条（持久化，含正文） |
   | 用量 | 一段时间内用了多少，花在哪里         | 聚合（持久化，仅数字） |
2. **每页只有一条筛选栏，不嵌套 tab。** 次要信息（日志、单条详情）放进抽屉或检查器，按需展开。
3. **三页之间可以下钻。** 运行页的请求行和用量页的明细行都能跳到会话页的对应步骤，这样跳转后不必重复筛选。
4. **观测是旁路。** 采集失败、队列满、轨迹库损坏都不能影响请求转发，也不能影响用量统计。

## 2. 已确定的决策


| #   | 决策           | 结论                                                                                                                                         |
| ----- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| E1  | 轨迹内容       | 存完整正文（用户已选 B）：用户消息、模型输出、推理摘要、工具调用与结果、系统提示词、工具定义。不存请求头和凭据                               |
| E2  | 存储隔离       | 轨迹单独存一个库 `<数据目录>/trajectory.db`。主库 `yi-token.db` 不膨胀；`.yitoken` 备份不包含轨迹；清空轨迹可以直接 `VACUUM`，甚至删文件重建 |
| E3  | 用量与轨迹解耦 | 用量统计仍以主库 `usage` 表为准，只新增 `step_id` 弱关联和耗时字段。**清理或关闭轨迹不影响用量**                                             |
| E4  | 数据模型层级   | 终端 → 会话 → 线程 → 回合 → 步骤 → 条目（见第 3 节）。一次代理请求等于一个**步骤**，不是一个回合                                        |
| E5  | 去重方式       | 前缀链：每个步骤只存"相对父步骤新增的条目"和本步输出；条目正文按内容哈希存为 blob 并压缩。总存储随步数线性增长，不随历史长度平方增长         |
| E6  | 会话归属       | 客户端提供的会话标识优先；没有时用前缀链匹配自动归并（见 4.3），不再用"首条消息哈希"这种容易误合并的兜底                                     |
| E7  | 采集开销       | 请求路径上只做两件事：克隆 `Bytes`（引用计数），以及把已有的 IR 流事件喂给 `Collector`。请求体解析成 IR、哈希、压缩、写库都放在采集线程      |
| E8  | 刷新方式       | 沿用现有 TanStack Query 轮询，但改为增量游标（`since_seq` / `changed_since`），不拉全量。Tauri 事件推送留作后续优化                          |
| E9  | 保留策略       | 天数（默认 30 天）与容量（默认 2 GiB）同时生效，先到先清，按会话整段删除。可全局关闭采集，也可按终端关闭                                     |
| E10 | 导航           | 侧边栏分"配置"（服务商、模型、终端）和"观测"（运行、会话、用量）两组                                                                         |

## 3. 领域模型

```
终端 Client            claude-code / codex / opencode / pi / deepseek-harness / api(全局路由)
└─ 会话 Session        一次 Agent 运行；来自客户端会话标识或前缀链归并
   └─ 线程 Thread      同一会话里独立的上下文：主线程、子 Agent、旁路调用（标题生成、压缩摘要等）
      └─ 回合 Turn     一次用户输入，到模型不再调用工具为止
         └─ 步骤 Step  一次代理请求（一个模型调用）
            └─ 条目 Item  消息 / 推理 / 工具调用 / 工具结果
```

为什么要有线程这一层：Claude Code 的子 Agent、Codex 的压缩，以及各客户端用小模型生成标题的请求，会话标识相同，但上下文完全不同。如果不拆开，轨迹会在两段无关的对话之间来回跳。deepseek-harness 的轨迹视图同样区分了主记录与嵌套的 Subtool 记录。

**工具结果的位置**：模型在步骤 N 输出工具调用，工具结果出现在步骤 N+1 的请求输入里。展示时按 `call_id` 把两者配对成一行"工具调用 → 结果"。

## 4. 采集

### 4.1 挂接点（`core/src/proxy/pipeline.rs`）


| 时刻           | 动作                                                                                                                                                                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 解析请求体之前 | 克隆原始 `body: Bytes`，记录 `requested_at`，抽取会话标识候选（4.3）。这里只做克隆，不解析                                                                                                                                                 |
| 流式响应       | 在 `stream_translator_with_usage` 的 `Source` 产出 IR `StreamEvent` 的位置加一个可选的 `Tap`，把同一批事件喂给 `responses::stream::Collector`。第一个内容增量到达时记录 `first_token_at`。**直通流与转换流共用这一挂接点，不做第二次解析** |
| 非流式响应     | 克隆上游响应 `Bytes`，交给采集线程用 `translate_response` 的同一套解析得到 IR                                                                                                                                                              |
| 结束           | 不论正常结束、上游报错、客户端断开，都会触发现有 `UsageGuard` 的 `Drop`。在同一个位置投递 `CaptureRecord`，因此"每个请求恰好一条"的保证不变                                                                                                |

`StreamTranslator` trait 增加 `fn tap(&mut self, tap: Box<dyn FnMut(&StreamEvent) + Send>)`，或者等价地在 `Source` 外包一层，具体在实施计划里定。

### 4.2 采集线程

1. 把请求 `Bytes` 用 `to_ir(inbound, ..)` 转成 IR 请求。超过 `OFFLOAD_THRESHOLD` 的请求体本来就会在阻塞池解析，所以采集线程不占 async worker。
2. 对每个输入条目、本步输出条目、系统提示词、工具定义：规范化 → SHA-256 → 已存在就跳过，否则 zstd 压缩后写入 blob。
3. 计算会话、线程、父步骤与回合号（4.3、4.4）。
4. 批量写库（每批最多 64 个步骤或 32 MiB，先到先写）。

**队列按字节限流**：在途总量上限 64 MiB。超限时丢弃正文，只保留步骤元数据，并标 `capture = "metadata_only"`。请求本身不受影响。

### 4.3 会话归属

按以下顺序判定，命中即停：

1. **客户端会话标识**，`key_source = "client"`：
   - Codex：`session_id` 请求头；回合号直接取 `x-codex-turn-id`。两者都已在 `headers.rs` 的转发白名单里。
   - Claude Code：请求体 `metadata.user_id`。当前已知版本的格式里带有 `_session_<uuid>` 片段，**需要抓包确认后才写入解析规则**。
   - opencode、pi、deepseek-harness：先抓包。没有确认之前一律走第 2 条。
2. **前缀链匹配**，`key_source = "chain"`：本请求的输入条目序列，如果以某个近期线程尾部步骤的"输入 + 输出"为前缀，就归入那个线程所在的会话，取最长匹配。只在同一终端内、且最近 12 小时内活跃的线程中查找。
3. **新会话**，`key_source = "new"`：以上都不命中时新建会话。

前缀匹配用"指纹"而不是存储哈希。原因是客户端回传的历史和代理当时记录的输出在格式上会有细微差异，例如推理签名被剥离、条目 ID 不同、Anthropic thinking 块被丢弃。指纹只取语义字段：角色、文本、工具名、规范化后的参数、`call_id`。每个步骤存一个 `tail_fp`（输入 + 输出序列的滚动指纹）。查找时对新请求的每个前缀长度算一次滚动指纹，命中内存里的尾部索引（LRU 2000 项）；内存未命中再查 `steps.tail_fp` 索引列。

会话标识只用于分组，不参与路由。

### 4.4 线程、父步骤与回合

- **线程**：在同一会话内，用 4.3 第 2 条同样的前缀匹配寻找父步骤；匹配不到就新开线程。
- **线程类型**（只影响展示，判错不影响数据）：
  - `main`：会话内第一个出现工具调用的线程。
  - `subagent`：首条用户消息与另一线程某个进行中工具调用的 `prompt` 参数相同（例如 Claude Code 的 Task 工具）；记录 `parent_thread_id` 和触发它的 `call_id`。
  - `side`：只有一步、没有工具定义或工具调用的线程，例如标题生成、摘要。
- **回合**：有 `x-codex-turn-id` 时直接使用。否则，当一个步骤相对父步骤新增的条目里含有带文本的用户消息（不是纯工具结果）时，开启新回合。
- **压缩 / 上下文重置**：会话标识相同但前缀匹配失败时开新线程，界面标注"上下文已重置"。

### 4.5 状态与停止原因

`stop_reason` 归一化为 `end`、`tool_use`、`max_tokens`、`refusal`、`error`、`cancelled`、`unknown`。来源依次是：IR `Response` 的状态与输出条目、HTTP 状态码、客户端断开时 `UsageGuard` 未 `finish`。

## 5. 存储

### 5.1 轨迹库 `trajectory.db`

独立的 r2d2 连接池，WAL，外键开启，迁移独立编号（`user_version` 从 1 起）。


| 表           | 关键字段                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sessions`   | `id` PK；`client`；`client_key`（可空，`UNIQUE(client, client_key)`）；`key_source`；`title`；`started_at`；`last_at`（索引）；`step_count`；`input_tokens`、`output_tokens`；`bytes`                                                                                                                                                                                                                                              |
| `threads`    | `id` PK；`session_id` FK 级联；`kind`；`parent_thread_id`；`spawn_call_id`；`started_at`                                                                                                                                                                                                                                                                                                                                           |
| `steps`      | `id` PK；`session_id`、`thread_id` FK 级联；`seq`（全库自增，作增量游标）；`parent_step_id`；`prefix_len`；`turn_no`；`client_turn_id`；`requested_at`、`first_token_at`、`finished_at`；`status`；`stop_reason`；`error`（截断到 4 KiB）；`inbound_protocol`、`upstream_protocol`；`provider_name`、`model`、`upstream_model`；四项 token；`system_blob`、`tools_blob`；`tail_fp`（索引）；`capture` ∈ {`full`, `metadata_only`} |
| `step_items` | `(step_id, side, ord)` PK；`side` ∈ {`input`, `output`}；`blob`；`kind`；`call_id`（可空，索引，用于配对）；`tool_name`                                                                                                                                                                                                                                                                                                           |
| `blobs`      | `hash` PK；`kind`；`raw_bytes`；`data`（zstd）；`truncated`                                                                                                                                                                                                                                                                                                                                                                        |

- `step_items` 的 `input` 侧只存 `prefix_len` 之后新增的条目。要还原步骤 N 的完整上下文，沿 `parent_step_id` 向上拼接（递归 CTE）。每隔 64 步写一次完整条目列表作为检查点，`prefix_len = 0` 且没有父步骤，避免长会话的回溯链过深。
- 系统提示词和工具定义单独成 blob。Claude Code 每个请求都带十几 KiB 的工具定义，按哈希存只占一份。
- 单条 blob 原文超过 1 MiB 时截断，保留首尾各 256 KiB，并标 `truncated`。`data:` 开头的内联图片只存媒体类型、尺寸和哈希，不存内容。

### 5.2 主库变更（`yi-token.db`）

`usage` 表新增可空列 `step_id`、`ttft_ms`、`duration_ms`、`status`、`session_id`。旧行保持为空，不回填。用量页的耗时类指标只统计非空行，并在界面上注明"自启用后统计"。

### 5.3 保留与清理

- 采集线程每写 256 个步骤检查一次，另外应用启动时检查一次。超过天数或容量时，从 `last_at` 最早的会话开始，按会话整段删除。
- 删除会话之后，用 `NOT EXISTS` 清掉不再被任何步骤引用的 blob，分批执行，每批 1000 个。
- 删除量累计超过库大小的 25% 时，空闲时执行 `PRAGMA incremental_vacuum`。
- 手动操作：删除单个会话、清空某终端、清空全部。清空全部时直接删除并重建 `trajectory.db`。

### 5.4 失败隔离

`trajectory.db` 打开失败或迁移失败时，记 error 日志，并把采集降级为关闭；设置页显示原因并提供"重建轨迹库"。主库和代理照常工作。

## 6. 实时运行数据（内存）

在 `proxy` 中新增 `LiveRegistry`，与 `Monitor` 并列：

- 在途请求表：`request_id`、终端、模型、开始时间、阶段（`waiting` 等待首 token / `streaming` / `done` / `error`）、已收到的输出 token。
- 最近完成的 500 条请求组成环形缓冲，每条带全局 `seq`。
- 每个条目带 `step_id`，用于跳转到会话页。代理重启后清空，不持久化。

## 7. 服务与命令接口


| 服务方法                                                                 | 说明                                                                                                                    |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `proxy.live(since_seq)`                                                  | 在途请求列表，加上 `seq > since_seq` 的已完成请求                                                                       |
| `sessions.list(filter, cursor, limit)`                                   | `filter`：终端、关键字（匹配标题）、时间范围、模型。按 `last_at` 倒序，键集分页                                         |
| `sessions.changed_since(seq)`                                            | 自游标之后有变化的会话 ID 与新游标，用于增量刷新列表和当前打开的轨迹                                                    |
| `sessions.get(id)`                                                       | 会话元信息、线程列表、汇总                                                                                              |
| `sessions.trajectory(session_id, thread_id?, before_turn?, limit_turns)` | 按回合分页，默认最近 20 个回合。返回已经投影好的"回合 → 步骤 → 记录"（见 8.3.1）。记录只带摘要和每条最多 2 KiB 的正文 |
| `sessions.step(step_id)`                                                 | 单步详情：完整输入（还原后的上下文）、输出、系统提示词、工具定义、计时、token                                           |
| `sessions.blob(hash)`                                                    | 按需取被摘要截断的正文                                                                                                  |
| `sessions.delete(id)` / `sessions.clear(client?)`                        | 删除                                                                                                                    |
| `settings.trajectory` 读写                                               | 是否采集、按终端开关、保留天数、容量上限；同时返回当前占用                                                              |
| `usage.report(filter)`                                                   | 现有接口加上 `client` 筛选与 `group_by` ∈ {`model`, `client`, `provider`}                                              |

类型用 `ts-rs` 导出到 `src/generated/`。列表接口不返回正文，正文只在 `trajectory`（摘要）、`step` 和 `blob` 里返回。

### 8.3.1 轨迹视图：对照 deepseek-harness 实现

结构照搬 `packages/client/ui-trajectory`：工具栏（`TrajectoryToolbar.tsx`）、时间线总览（`TrajectoryTimeline.tsx` 与 `timeline.ts`）、账本表格加检查器（`TrajectoryTable.tsx`）、虚拟行（`trajectory-virtual-rows.ts`）。区别在数据来源：deepseek-harness 读的是 Agent 自身的会话事件，yi-token 读的是代理采集到的步骤，所以需要下面这张映射表。

**记录类型**（对应其 `TrajectoryCellKind`）


| 类型        | 标签色     | yi-token 的来源                                                                             |
| ------------- | ------------ | --------------------------------------------------------------------------------------------- |
| `system`    | 中性       | 线程首步的 `system_blob` / `tools_blob`；后续步骤这两个哈希变化时再生成一条，检查器给出差异 |
| `user`      | 默认       | 新增输入里带文本的用户消息；它开启新回合（`opensTurn`）                                     |
| `message`   | 紫         | 本步的助手输出：文本加推理（`thinkingDetail`）                                              |
| `tool`      | 琥珀       | 本步输出的工具调用，按 `call_id` 与下一步输入里的工具结果配对；行内显示"调用 → 结果摘要"   |
| `subtool`   | 琥珀（浅） | 子 Agent 线程，挂在触发它的 `tool` 记录下面；展开后显示该线程的记录，缩进一级               |
| `compacted` | 灰         | 线程重置或上下文压缩：会话标识相同，但前缀不匹配                                            |

**账本**（两列表格：类型标签列、内容列）

- 每条记录一行，行高 30px；内容超出时省略，`title` 显示全文。
- **请求边界**：每个步骤的第一条记录左侧显示一个请求标记（"请求 #N"），颜色表示状态（完成 / 进行中 / 失败）。点击标记打开该请求的检查器。
- **回合标签**：回合首行显示"轮次 N"，窄宽度时显示为 `#N`；当前回合左侧有竖条。
- **折叠**：双击回合首行，或使用工具栏的"轮次"按钮，把回合折叠成一行摘要（"N 步 · M 次工具调用"，行高 20px）。双击助手行，或使用"调用"按钮，把它后面的工具调用折叠成"M 次工具调用 · 工具名列表"。折叠算法照搬 `collapseTurnRecords` / `collapseAssistantRecords`。
- **状态**：工具没有结果，或请求还在途（来自 `LiveRegistry`），显示"进行中"；`stop_reason` 为 `error` / `cancelled` 显示"失败"。在途请求不流式显示正文，只显示阶段（等待首 token / 生成中）。
- **搜索**：只在已加载的窗口内过滤，范围是类型标签、摘要和结果摘要。
- **虚拟化**：`@tanstack/react-virtual`（项目已有依赖）。行的 key 用记录的稳定 ID（`step_id` + 序号，或 `call_id`），前插更早的页时不会错位。
- **跟随末尾**：打开时定位到末尾；用户向上滚动就暂停跟随，滚回底部后恢复。
- **加载更早**：第一行是"加载更早的回合"控件，每次加载 20 个回合。

**时间线总览**

- 三条泳道：0 = system / user，1 = message / compacted，2 = tool / subtool（照搬 `laneFor`）。
- 三种投影（照搬 `TrajectoryTimelineMode`）：等宽序列；实际时长；实际时间（压缩空闲段）。
- 助手条分成两段：TTFT 段（`requested_at` → `first_token_at`）和生成段（`first_token_at` → `finished_at`）。
- 工具条的时长 = 下一步 `requested_at` − 本步 `finished_at`，也就是客户端执行工具加上发起下一次请求的间隔。检查器标注为"估算"，因为代理看不到工具真正的起止时间。
- 交互：拖选一个区间，账本就只高亮该区间内的记录（`trajectoryTimelineFocusIndexes`）；滚轮缩放；右键单击清除选择；右键拖动平移；悬停 500ms 显示精确时间。
- 回合边界画成竖线。

**检查器**（右侧可调宽度的抽屉，页签随类型变化，对照 `detailTabs`）


| 选中对象           | 页签                                                                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `system`           | 系统提示词 · 工具 · 差异（仅变更时）                                                                                                                                                              |
| `user` / `message` | 概述 · 预览 · 原始内容                                                                                                                                                                            |
| `tool`             | 概述 · 参数 · 结果 · Schema（该工具在调用时的定义）· 计时                                                                                                                                       |
| 请求标记           | 用量（输入 / 缓存 / 输出 / 推理 token）· 选项（模型、上游模型、服务商、入站和上游协议、路由模式）· 计时（开始时间、TTFT、生成时长、总时长、输出速率）· 完整上下文（按需从 `sessions.step` 加载） |

- "预览"页签把文本当 Markdown 渲染，新增依赖 `react-markdown` + `remark-gfm`；"原始内容"页签按原样等宽显示，参数和结果是 JSON 时以树形展示。
- 截断的正文显示"已截断，原文 X KiB"，并提供"加载全文"（调用 `sessions.blob`）。

**投影放在后端**
deepseek-harness 在前端用 `layout.ts` 把事件投影成记录。yi-token 把这一步放到 Rust（`core/src/services/trajectory_view.rs`），`sessions.trajectory` 直接返回"回合 → 步骤 → 记录"。原因有两个：这个项目只有 `cargo test`，没有前端单元测试框架；工具调用与结果的配对、system 变更检测、子 Agent 挂接都需要跨步骤查数据，放在库这一侧做更简单。前端只负责展示状态：折叠、搜索、时间线几何计算、虚拟化。

## 9. 测试

**Rust（`core/tests/`）**

- 采集挂接：直通流、转换流、非流式三种路径下，`Collector` 得到的输出与客户端实际收到的一致；客户端断开时 `stop_reason = cancelled` 且已收到的内容被保留；上游 500 时 `error` 有值。
- 用 `wiremock` 构造一个 5 步的工具循环，断言只产生 1 个会话、1 个线程、1 个回合，`step_items` 的输入侧每步只有新增条目，并且还原出的完整上下文与第 5 步的请求体等价。
- 前缀链：推理签名被剥离、条目 ID 改变时仍然能匹配；两个不同会话的首条消息相同时不会被合并。
- 子 Agent：Task 工具调用期间出现的新线程被标为 `subagent`，并正确关联 `parent_thread_id`。
- 保留：按天数和容量删除整段会话；被其他会话引用的 blob 不会被删。
- 隔离：队列满时请求成功、`usage` 照常写入；`trajectory.db` 不可用时代理照常工作。
- 迁移：主库 `usage` 新列；轨迹库从零建库。
- 性能基线：一个 4 MiB 请求体经过代理时，相对关闭采集，p50 额外延迟小于 1 ms。

## 11. 需要审阅时确认

1. 默认保留 **30 天 / 2 GiB**，采集**默认开启**，首次进入会话页时提示。
2. 新增依赖 `zstd` crate。它需要 C 编译器，但 `rusqlite` 的 `bundled` 特性已经在所有打包平台（Windows x64/arm64、macOS、Linux）上编译 C 版 SQLite，所以不增加新的工具链要求。
3. 线程类型的判定是启发式的，只影响展示。判错时，用户只会看到一个子 Agent 被显示成普通线程。
4. 第 0 期抓包结论如果和 4.3 的假定不符，以抓包为准修订本文件。
